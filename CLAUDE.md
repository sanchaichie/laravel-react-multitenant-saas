# Project: react-saas (multi-organization SaaS, React + Laravel)

A rebuild of `../saas-starter` (Laravel + Nuxt) with a React frontend, made to learn React. **Tasks** take the place of saas-starter's Projects. Each feature is rebuilt plan by plan, with saas-starter's code and tests as the reference. Open the matching saas-starter file before writing something it already solved, but don't copy Nuxt/Vue patterns into `web/`.

## Stack
- `api/`: Laravel (latest stable), PHP 8.4+, PostgreSQL (`react_saas`, tests `react_saas_test`), Sanctum (token auth), Pest
- `web/`: Vite + React 19 + TypeScript (strict), React Router, TanStack Query, Zustand, shadcn/ui + Tailwind v4, react-hook-form + zod, Vitest. Node 22 (`web/.nvmrc`)
- Local: macOS, Postgres running locally, API on :8100, Vite on :5173. saas-starter keeps :8000/:3000 (dev) and :8011/:3011 (e2e), so both repos can run at once.

## Commands
- API: `cd api && PHP_CLI_SERVER_WORKERS=4 php artisan serve --port=8100 --no-reload`, `php artisan migrate`, `php artisan test`
- Queue worker: `php artisan queue:work`
- Web: `cd web && npm run dev`, `npm run build`, `npm run lint`, `npm run typecheck`, `npm test`
- Always run `/verify` (or `php artisan test` and `npm run build`) before saying a task is done.
- CI (`.github/workflows/ci.yml`) runs the `/verify` steps on every push to `main` and every PR: Pint and Pest against a Postgres service (`react_saas_test`), plus oxlint, typecheck, Vitest and build. Keep it in step with `verify.sh` when a check changes. Dependabot (`.github/dependabot.yml`) only updates the workflow's actions.
- Never wipe a database. Dev and test share one Postgres, and `--env=testing` without an `.env.testing` uses `.env`. `.claude/hooks/block-destructive-db.sh` blocks `migrate:fresh`/`refresh`/`reset`/`rollback`, `db:wipe`, `dropdb` and `DROP`/`TRUNCATE` for Claude. In the app, `AppServiceProvider::guardDestructiveDatabaseCommands` refuses them on any database whose name doesn't end in `_test` (override for one run: `DB_ALLOW_DESTRUCTIVE_COMMANDS=true`). Pest rebuilds its own database.

## Multi-organization model
- Users belong to many organizations via the `organization_user` pivot. Roles are per organization: rows of `roles` (`App\Models\Role`, tenant-owned) with a set of `App\Enums\Permission`. Policies check permissions, never role names.
- No tenant in the URL or subdomain. The active organization is stored server-side (`users.current_organization_id`).
- Switching: `POST /api/organizations/{id}/switch`. Verify membership on the server every time.
- Tenant-owned models use the `BelongsToOrganization` trait (global scope + auto-set `organization_id` on create).
- NEVER accept an organization id from the frontend as proof of access. Always derive it from the authenticated user.
- Every tenant-owned feature needs a Pest test proving org A cannot read or write org B's data.
- `App\Support\CurrentOrganization` (scoped: fresh per request and job) is the only way to know the current organization: `id()`, `role()`, `get()`; `set()` for jobs and tests. It re-checks membership on every request. Routes that act on it go in the `organization` middleware group in `routes/api.php` (403 "No active organization." without one). In jobs and listeners use `run($organization, fn () => ...)`, which restores the previous state, not a bare `set()`.
- `apiFetch` sends `X-Organization-Id` (the organization the tab thinks is current). It is a precondition only, never used to choose: the `organization` middleware answers 409 `organization_changed` when it differs (another tab switched), and `apiFetch` then reloads `/api/me` and drops `['org']` queries.
- Roles (plan 08): `organization_user.role_id` and `organization_invitations.role_id` point at one through composite foreign keys `(organization_id, role_id)`, so a role is always in the row's own organization. Every organization starts with Owner, Admin and Member (`CreateDefaultRoles`, from `App\Enums\DefaultRole`); afterwards they're ordinary rows, except Owner (`is_owner`: every permission, can't be edited or deleted, never fillable). Never decide anything by a role's name. A `role_id` from the client is only a reference: validate it with `ValidatesRoleId` (scoped `Rule::exists`), then load it through the scope. Assigning a role locks it `FOR SHARE` (`LocksRole`) right after the organization row; `DeleteRole` locks it `FOR UPDATE` and refuses while members have it (invitations lose it instead and can't be accepted). `Membership::role()` and `OrganizationInvitation::role()` skip the organization scope (the foreign key already limits them) because the switcher and the join page show roles of other organizations. `CurrentOrganization::roles()` loads the organization's roles once per request for lists.
- Registration creates a personal organization the user owns.
- Pest helpers (`tests/Pest.php`): `userInOrganization(DefaultRole $role, $name)`, `addMember($org, DefaultRole|Role)`, `createRole($org, $name, $permissions)`, `roleId(DefaultRole, ?$org)` (to send as `role_id`; default: the logged-in user's current organization), `auditEntries(?$org, ?AuditAction)`, `$organization->role(DefaultRole)`, and `inOrganization($org, fn () => ...)` to create tenant-owned rows. `TestCase::call()` forgets scoped instances, so each test request resolves the organization afresh.

## Tasks (the reference feature, plan 07)
- Tenant-owned: title, description, status (`todo`, `in_progress`, `done`; an enum), priority (`low`, `medium`, `high`), `due_date` (date, nullable), `assignee_id` (nullable, must be a member of the same organization; set to null when they leave), `created_by`.
- The list filters by status, assignee, priority, overdue and search, and is paginated. Filters live in the URL.
- Permissions: anyone in the organization lists and views; `tasks.create` (every default role) creates, edits the tasks you created or are assigned to, and deletes the ones you created; `tasks.manage` (Owner, Admin) edits and deletes any task. A role without `tasks.create` (a viewer) only reads.
- The assignee is checked twice: the form request (`Rule::exists` on `organization_user` scoped to the current organization) and the actions (`LocksAssignee`: a `FOR SHARE` lock on that membership, so `RemoveMember` waits and then unassigns).
- Overdue (due before the API's today, not done) is decided by the server: `Task::scopeOverdue()` for the filter, `is_overdue` in the resource. The app never compares dates; `due_date` is a plain `YYYY-MM-DD` string.
- The `organization` middleware runs before route model binding (`bootstrap/app.php`), so a missing organization or a stale tab gets its 403/409 instead of a 404 from the scoped binding.

## Backend conventions
- Thin controllers. Business logic in Action or Service classes.
- Use Form Requests for validation and API Resources for responses.
- Migrations only. Never edit an existing migration that has been committed; add a new one.
- Do not edit `.env`. Add new keys to `.env.example` with a comment.
- Features that reach other people or cost money (invitations, billing, AI) use the `verified` middleware (403 `email_unverified`). Joining doesn't: accepting an invitation verifies the email, since its link reached that inbox (`AcceptInvitation`).
- Policies check `App\Enums\Permission` through `CurrentOrganization::can()` / `role()->can()`, never role names. You may only act on, or give, a role your own role `includes()` (its permissions are a subset of yours; only Owner includes Owner): that's what keeps admins away from owners. Managing roles (`roles.manage`) is stricter: you grant only permissions you have, and edit or delete only roles yours `includesStrictly()` (not your own, not a peer's). An organization always keeps an owner (`EnsuresAnOwnerRemains`: lock the organization row first, then the owner rows in id order). Resources return `can` flags (and `assignable_roles` for members, `invitable_roles` for invitations, as `{id, name, is_owner}`) so the app never repeats the rules.
- Email: mail and notifications are queued (tries + backoff) and take plain values. Links point at the app (`config('app.frontend_url')`). Locally they go to `storage/logs/laravel.log` and need `php artisan queue:work`; `servers.sh start --mail` sends them at once.
- Tokens are only issued through `IssueToken`. A new way to log in must go through the same checks (two-factor from plan 15, suspension from plan 17). It names the token (the client's `device_name`, or `DeviceName::fromUserAgent()`: "Chrome on macOS") and stores the IP address and User-Agent for the list of signed-in devices.
- Account (plan 14): user-level routes outside the `organization` group (`/api/account`, `/api/account/email|password|devices`), so they work with no current organization and never touch tenant data except through `DeleteAccount`. Account events aren't in any organization's audit log. Changing your email is pending until confirmed: `PUT /api/account/email` (current password) stores `users.pending_email` and mails a signed link to the new address (`ConfirmEmailChange`, the app's `/confirm-email`, posted back to `POST /api/account/email/confirm/{id}/{hash}` while logged in), plus a notice to the current one; until then the account keeps its email, so its owner can log in and reset with it. Confirming (on the locked user row, re-checking the request and the current token) switches the email (verified), keeps the old one in `previous_email`, revokes your other tokens (`whereKeyNot` the current one) and mails the old address `EmailChanged` with a signed 7-day undo link (`/revert-email` → `POST /api/account/email/revert/{id}/{old}/{new}`, no login): it puts the old address back (verified), revokes every token and mails it a password reset, so someone who had the password can't keep the account. A newer request replaces the confirmation link; cancelling (`DELETE /api/account/email/pending`), a password change or a password reset clears it. At most 3 confirmation emails a day go to one address, whoever asks (answered the same). Changing your password needs the current one and revokes your other tokens; a password reset revokes all of them, verifies the email and logs in through `IssueToken`. Email, password and delete share a `current-password` limit (5 a minute, 20 an hour) on top of their own. Forgot password always answers the same (no account discovery). `DeleteAccount` locks each organization row, then its owner memberships, then the rest (id order); it refuses (422 on `account`) while you're the last owner of an organization with other members, deletes organizations where you're alone (cascading foreign keys take their data), and leaves the others through `RemoveMember` (audited there). Email change requests: 6 a minute (`account-email`) and 10 sent a day (`ChangeEmail::PER_DAY`).
- Email links point at the React app (`config('app.frontend_url')`), which posts them back to the API.

## Frontend conventions
- Function components and hooks, TypeScript strict, no `any`. Files: components in PascalCase `.tsx`, hooks named `useX`.
- Layout of `web/src/`: `routes/` (one file per page, wired in `router.tsx`), `features/<feature>/` (that feature's query hooks in `api.ts`, plus its components), `components/ui/` (shadcn-generated; add with `npx shadcn add`, don't hand-edit without a reason), `components/` (shared), `stores/` (Zustand), `lib/` (`api.ts`, `apiErrors.ts`, `safeRedirect.ts`), `types/api.ts`.
- API calls go through `apiFetch` (`lib/api.ts`). It adds the base URL (`VITE_API_BASE`), `Accept: application/json` and the Bearer token, and clears the session on a 401. Components never call it directly: they use TanStack Query hooks from `features/<feature>/api.ts`. No `useEffect` + `useState` for loading data.
- Query keys for org-scoped data start with `['org', currentOrganizationId, ...]`; switching organization removes them, and goes to the root of the current section (`/tasks/42?assignee=7` → `/tasks`), since ids and filters belong to the old one. Mutations invalidate what they change; a detail page still mounted marks its own query stale (`refetchType: 'none'`) instead of removing it, which would refetch it.
- List filters live in the URL (`useSearchParams`), parsed on every render and never copied into state; unknown values are dropped. Filter changes replace the history entry and reset the page; page links push one. Typing is debounced with `useDebouncedCallback`.
- The current organization comes with the user (`user.current_organization`, with the role): read it with `useCurrentOrganization()`, never copy it into other state. The organization list is `organizationsQuery` (`['organizations']`, user-level). Switch and create go through `useSwitchOrganization` / `useCreateOrganization`, which also drop `['org']` queries.
- Logged-in pages render in `AppLayout`: the shadcn sidebar (`AppSidebar`: organization switcher, the `navigation` list, `UserMenu` with appearance and log out, version). A new page adds its entry to `navigation`. Appearance is `next-themes` (`ThemeProvider` in `AppProviders`, `dark` class on `<html>`); pages use the theme tokens (`bg-background`, `text-muted-foreground`, ...), not fixed colors.
- Server data lives in TanStack Query. Zustand holds only client state: the auth store (token, current user) and the current organization. Select slices (`useAuth(s => s.user)`), not the whole store.
- The token is kept in `localStorage` (no SSR, so no httpOnly cookie without a proxy). That makes XSS a token theft: no `dangerouslySetInnerHTML` on user content, and nothing secret in `VITE_*` (it ships to the browser).
- React Router in data mode: routes are declared in `router.tsx` (`createBrowserRouter`); layouts and guards are pathless layout routes with `<Outlet>`. Data comes from TanStack Query, not route loaders. Import `RouterProvider` from `react-router/dom` (it supports `flushSync`).
- Route guards are components (`RequireAuth`, `RequireGuest`) around route groups, in place of Nuxt middleware. `?redirect=` goes through `safeRedirect`. They redirect by reacting to the auth store, so code outside React (like `apiFetch` on a 401) only clears the session and never navigates.
- `bootstrapSession()` loads `/api/me` once in `main.tsx` before the first render; only the token is persisted (`localStorage` key `auth`).
- Tests: Vitest + Testing Library (jsdom). `src/test/utils.tsx` has `renderApp(path)` (the real routes in a memory router), `mockApi({ 'POST /api/login': (init, url) => ... })` (matched without the query string, which the handler reads from `url`; fails on any unmocked request), `test/tasks.ts` (`makeTask`, `taskPage`, members), `logIn()`, the `acme`/`beta` organizations with `organizationList()` and Acme's `ownerRole`/`adminRole`/`memberRole`, and `logOutFromMenu()`. Logged-in pages load `GET /api/organizations` (the switcher), so mock it. `src/test/setup.ts` stubs the browser APIs jsdom lacks (`matchMedia`, `ResizeObserver`, pointer capture). Radix submenus: drive them with the keyboard in tests. Lint is oxlint (`.oxlintrc.json`: rules of hooks, exhaustive deps, no `any`).
- Forms use react-hook-form with a zod schema; 422 errors are mapped onto fields.
- Use shadcn/ui components before writing custom ones. Check the shadcn MCP before guessing a component's API.
- Show or hide controls with `useCan(permission)` (current organization) or the resource's `can` flags; the API decides. Confirm destructive actions with `components/ConfirmDialog`. A Radix `Select` in a react-hook-form form goes through `Controller` (it isn't a native input).
- Work that must happen after a mutation even if the component unmounts (leaving an organization drops the list it's in) goes in `useMutation({ onSuccess })`, not in `mutate(vars, { onSuccess })`: TanStack Query skips the latter once its component is gone. Use `onMutate`'s return value (`context`) for anything read before the request.
- Every page has loading, empty and error states. Dates render with a fixed locale and time zone.

## Audit log (plan 09)
- Tenant-owned models people create, edit or delete use the `Auditable` trait (`Task`, `Role`): it records `<name>.created|updated|deleted` with the changed values as the API serializes them. Keys, `organization_id`, timestamps and `$hidden` are never recorded; add others to `$auditExclude`. Override `auditLabel()` (the name kept with the entry) and `auditChanges()` to keep names instead of ids (`Task` records `assignee: {id, name}`). It throws if the model isn't in the current organization. Builder updates skip it: change audited rows one by one, or record the change yourself (`RemoveMember` counts unassigned tasks).
- Other notable actions (organization created, invitations, joining, role changes, removals) call `App\Actions\Audit\RecordAudit` inside their transaction (pass `actor:` when nobody is logged in yet, as when registering), so a refused or rolled-back change leaves no entry. Pass `organization:` when not acting in it as the current organization (joining, creating). Setup code that shouldn't be logged runs in `Model::withoutAuditing()` (`CreateDefaultRoles`).
- Every new event is an `App\Enums\AuditAction` case with a label and group. Never log secrets, tokens or passwords. Keep names (role, person) in the entry, so it still reads once they're gone.
- Reading needs `audit_log.view` (Owner, Admin). IP addresses only for owners; email addresses (invitees, members who left) only with `members.invite` (`AuditLogResource`). Entries are append-only (`AuditLog` refuses updates and single deletes); `model:prune` (daily) deletes them after `AUDIT_RETENTION_DAYS`.
- The page (`/audit-log`) loads with `useInfiniteQuery` and the API's cursor pages ("Load more"); filters live in the URL. A nav entry can name a `permission` (`AppSidebar`) to show only to roles with it.
- Pest: `auditEntries($org, AuditAction::...)`. `jsonb` reorders object keys, so compare `changes` and `metadata` with `toEqual`, not `toBe`.

## AI layer (plans 10–13)
- All AI calls happen in Laravel; provider keys never reach `web/` (nothing AI-related in `VITE_*`).
- Code against `App\Ai\Contracts\AiClient`. Provider and model come from `config/ai.php` and `.env` (`AI_PROVIDER`: `anthropic` over Laravel's HTTP client, or `fake`). The container wraps the provider in `RecordingAiClient`, so every call, failed ones too, lands in `ai_usage` (organization, user, feature, model, tokens, cost from `config('ai.pricing')`).
- Prompts are classes in `app/Ai/Prompts` (`TaskSummaryPrompt`), never inline strings. Wrap user content in tags, escape `<`/`>`, and say in the system prompt that tagged content is data, not instructions (prompt injection). Only the one record's own fields go in, never another organization's data.
- Ask for structured JSON (`schema`) and validate it with the prompt's `rules()` before saving. AI output is saved as a draft someone approves (and may edit); it never changes the record or triggers anything on its own.
- Slow AI work is a queued job extending `App\Jobs\OrganizationJob` (stores the organization id at dispatch; `SetCurrentOrganization` runs it inside `CurrentOrganization::run()`; `inOrganization()` for `failed()`), with `RateLimited('ai')`. Jobs retry until `retryUntil()` (20 minutes, `maxExceptions` 3), not a try count, since rate-limited releases count as tries. Timeouts nest: HTTP 60s < job 75s < queue `retry_after` 90s. `AiUnavailable` (429, 5xx, timeouts) is retried; `AiRequestFailed` (4xx, refusal, `max_tokens`, invalid output) fails at once.
- Rate limit AI per organization: `throttle:ai` on routes that start AI work (key `request:{org}`; jobs use `job:{org}`). Routes that start AI work are also `verified`; work started as a side effect (summaries on task create) checks the creator's verified email and its own key (`ai-auto:{org}`), skips quietly otherwise, and runs under `rescue()` so it never fails the action that triggered it. Requesting and reviewing follow who may edit the record, and requesting also needs `ai.use` (below).
- Summaries (`TaskSummary`): `pending → draft → approved | rejected`, or `failed`. At most one pending and one approved per task (partial unique indexes). Requests and reviews lock the task row first. The job saves only if the row is still pending. `source_hash` gives the resource its `stale` flag; a pending one older than `STALE_AFTER_MINUTES` (30, above the job's retry window) is `stuck`, and asking again replaces it. Summaries point at their task through a composite key `(organization_id, task_id)`. `ai:summarize-tasks` backfills (audit `source: backfill`, no actor).
- Permissions (plan 11): `ai.use` to ask for AI work (Admin, Member; requesting a summary needs it *and* edit access to the task, reviewing only edit access), `ai_usage.view` for the AI usage page (Admin), `ai_budget.manage` to change the budget (no default role, so Owner only). Automatic summaries and the backfill check the creator's role for `ai.use`.
- Budget (plan 11): `App\Ai\AiBudget`, per organization per UTC month: `organizations.ai_monthly_budget_usd` (never fillable; `null` = `AI_MONTHLY_BUDGET_USD`, `0` = AI off) against the sum of `ai_usage.cost_usd`. The container builds `BudgetedAiClient(RecordingAiClient(provider))`: a call over budget throws `AiBudgetExceeded` (an `AiRequestFailed`, code `budget_exceeded`, never recorded; 402 `ai_budget_exceeded` in a request) before reaching the provider. Anything that queues AI work checks first (`ensureAvailable()` in `RequestTaskSummary`, `exceeded()` in the listener and backfill), so nothing is queued that can't run; a job that runs over budget fails its work with that code. Calls running at once can go slightly over (accepted). A call with no current organization is refused (`NoCurrentOrganization`): nobody would be billed. The budget protects an organization from itself, not the operator's bill (any owner can raise theirs to $10,000). `GET /api/ai-usage` (`AiUsageReport`) and `PUT /api/ai-budget` (`UpdateAiBudget`, audited `ai_budget.updated`). Pest: `recordAiUsage($org, $usd, [...])`.
- Controllers take `CurrentOrganization` as an action parameter, never in the constructor: the router reuses controller instances (tests, Octane), so a constructor-held one keeps the first request's organization (`ControllerReuseTest`).
- Interactive AI (writing help, later chat) streams; background work (summaries) is queued. `AiClient::stream($request, $onText)` reports each piece of text to the callback (return `false` to stop: stop reason `aborted`), through the same wrappers as `generate()`: budget and organization check, recording (a stopped stream is `succeeded` with `error_code = aborted`; a broken-off one is `failed`, with the tokens so far; output tokens of a partial answer are estimated at 4 characters per token). `AnthropicClient` parses the provider's SSE and enforces `AI_STREAM_TIMEOUT` as a total deadline in its read loop (each read waits at most 30s), so a stalled provider can't hold a worker.
- A streamed endpoint returns `App\Http\Responses\AiEventStream` (server-sent events `delta {text}`, `done {model}`, `error {message}`; `X-Accel-Buffering: no`). Once it starts the status is 200, so permission, validation, the budget (`ensureAvailable`) and a stream slot (`AiStreamSlots`: at most 2 per organization, 2 per user across organizations, and `AI_MAX_CONCURRENT_STREAMS`, 3, on the server, below the PHP workers; 429; the stream releases it, so give it back yourself if anything between taking it and returning the stream throws) are checked before returning it. It runs as the organization that authorized it (`CurrentOrganization::run`), keeps going when the browser leaves (`ignore_user_abort`) only to stop the call and record it, and releases its slot. Each stream holds a PHP worker: the dev and e2e servers run `PHP_CLI_SERVER_WORKERS=4`.
- Writing help (plan 12): `POST /api/tasks/writing-help` (new task) and `/api/tasks/{task}/writing-help` (`TaskPolicy::writeWithAi`: `ai.use` + create or update; `verified`, `throttle:ai`), `TaskWritingPrompt` (feature `task_writing`; only the submitted title and description, in `<draft>` tags; plain text, at most 5000 characters or it ends with `error`). Nothing is saved: the answer goes into the form for the user to save. `TaskResource` has `can.write_with_ai`.
- Task chat (plan 13): `GET|POST|DELETE /api/tasks/{task}/chat` (`TaskPolicy::chat`: view + `ai.use`; POST also `verified`, `throttle:ai`). History is private: every query goes through `TaskChatMessage::conversation($task, $user)`, nobody (not even Owner) reads another member's, and it isn't audited. `task_chat_messages` points at its task through `(organization_id, task_id)` and at the membership through `(organization_id, user_id)`, both cascading: deleting the task, or removing a member (or leaving), deletes those chats in the database, so new code needs no cleanup. `SendTaskChatMessage` takes the stream slot, then saves the question and an empty `stopped` answer together, and the stream's `onEnd($text, $outcome, $model)` hook (on `AiEventStream`) updates that row by id: `complete`, `stopped` (with the text so far) or `failed`. A Clear meanwhile isn't undone, and the order stays right. `TaskChatPrompt` (feature `task_chat`): the task's fields and approved summary in `<task>` tags as data, the user's last 20 messages (failed answers dropped, same-role turns joined, starting with the user). `TaskResource` has `can.chat`.
- Web streaming: `apiStream()` (`lib/apiStream.ts`, `fetch` + `ReadableStream`, not `EventSource`, which can't send the token or a body) goes through `apiRequest` like `apiFetch` (headers, 401, 409, `ApiError` before the stream), and `lib/sse.ts` parses events across chunks. Components use `useAiStream()` (`hooks/`): `{text, status: idle|streaming|done|error|stopped, error, start, stop, reset}`; `start` resolves with how the stream ended (`done`, `error` with its message, or `cancelled`) and rejects only when the request is refused (show why); a stopped, replaced or unmounted stream never changes state again. The chat (`features/taskChat`) shows the saved history (TanStack Query) plus the live exchange, combined during render, and refetches the history when an answer ends.
- Web: `features/taskSummaries`. The card polls with `refetchInterval` while pending (3s), stops after 60s (`gaveUpOn`), and writes mutation answers into the cache with `setQueryData`. The summary's key lives under the task's detail key, and editing a task invalidates it.
- Tests never call a real provider: `TestCase` binds `FakeAiClient` as `$this->ai` (`push()` a response, JSON or exception; `assertSent`, `assertNothingSent`) and calls `Http::preventStrayRequests()`. Provider tests use `Http::fake()`. `pushStream([...pieces])` queues a streamed answer (an exception among the pieces is thrown there; `FakeAiClient::ABORT` stops). e2e servers always run with `AI_PROVIDER=fake` and `AI_FAKE_STREAM_DELAY_MS=60`. Pest: `createSummary($org, $task, TaskSummaryStatus::Draft)`, `createChatMessage($org, $task, $user, ChatMessageRole::User, 'text')`, `sseEvents($response)` (a streamed response's events); Vitest: `makeTaskSummary()`, `noSummary`.

## Learning mode
The point of this repo is to learn React.
- Every plan's Frontend section lists the **React concepts** it introduces, one line each, compared with the Vue/Nuxt equivalent (e.g. `useState` ↔ `ref`, `useMemo` ↔ `computed`, TanStack Query ↔ `useAsyncData`, Zustand ↔ Pinia, React Router ↔ Nuxt pages, `children` ↔ slots).
- While building, explain each non-obvious React choice in a line or two.
- When the user says they'll write a piece themselves, leave a stub with a TODO listing the steps, then review their code instead of writing it.

  - Read-only reviewers: `code-reviewer`, `security-auditor`, `tenant-isolation-reviewer`, `database-reviewer`, and `ui-reviewer` (browser; runs on Sonnet in quick mode, checking only the items listed, unless asked for a "full sweep").
  - `flow-tester` (browser + curl; Sonnet) runs a plan's Flows end to end, emails included, and returns a results table. It doesn't edit code, uses only `e2e-ft-*` accounts and removes them; a hook limits its `servers.sh` use to `status`, `errors` and `cleanup e2e-ft-`.
  - `laravel-test-writer` can edit only `api/tests/`, enforced by a hook.
- Hooks: `block-destructive-db.sh` (every Bash call, subagents included) refuses commands that wipe or drop database data.
- Before reporting a change as done, run the reviewers that fit, in parallel:
  - always code, security and tenant isolation (once organizations exist);
  - database when there are migrations or queries;
  - UI when pages change.
- After the tests pass, when the plan has Flows, start the servers with `--mail` and run `flow-tester` on them (in the background, alongside `ui-reviewer` if it runs).
- MCP: `playwright` (headless browser for e2e and UI review) and `shadcn` (component registry and docs).

## Workflow rules
- Plan first for anything touching more than 3 files, then wait for approval.
- Plans live in `docs/plans/NN-task-name.md` (named after the task) with a Status line: Proposed → WIP (on approval) → Done (when committed, with commit hashes). Keep the index in `docs/plans/README.md` in sync.
- Build in small steps: one feature, tests passing, then commit.
- Docs change in the same commit as the code they describe: `.env.example` (new keys), `CLAUDE.md` (conventions, commands, tooling), root `README.md` (setup, run steps, features). `/ship-plan` checks this.
- From plan 03 on, a new page or a user-visible feature gets a README screenshot in the same plan: a PNG in `docs/screenshots/` plus a line in the README "Screenshots" section, captured with the Playwright MCP from e2e demo data (light mode, 1280×800, `e2e-*` accounts cleaned up). Retake an existing shot when a change makes it out of date.
- Commit message format: `type(scope): summary` (e.g. `feat(web): add task list filters`).
- Ask before adding a new dependency and say why it's needed. The stack listed above is already approved.
